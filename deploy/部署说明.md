# 知识库服务部署

前端仍按原流程执行 `npm run build:future`，由宿主机 Nginx 提供静态文件。知识库后端单独放到 `/workspace/course-knowledge`，Git 仓库是 `https://github.com/wimpama/hagongchengnuclear_kg.git`，当前分支为 `master`。

一套 Compose 项目 `course-knowledge` 包含 Rust API 和私网 Qdrant，两个网站共用。按原始 Host 分别进入 dev / prod SQLite、向量集合与 OSS 桶：`futuredev.artz.zone` 和本地进入 `futuredev`，`future.artz.zone` 进入 `futureprod`。Rust 只监听宿主机回环 `127.0.0.1:8080`；Nginx 在宿主机上，保留现有反向代理方式即可。

## 一、首次准备后端

本节命令在 Ubuntu 服务器执行。需要 Git、Python 3、`flock`（Ubuntu 的 util-linux 提供）和可访问 Docker daemon 的 Docker Compose。此前服务器核查已发现 Docker / Compose；实际部署前复查，脚本不会安装或重启 Docker。

```bash
git --version
python3 --version
docker compose version
docker info
command -v flock

git clone --branch master https://github.com/wimpama/hagongchengnuclear_kg.git /workspace/course-knowledge
cd /workspace/course-knowledge
cp env.example .env
chmod 600 .env
nano .env
```

先将本地后端代码提交并推送到对应仓库，服务器才能拉到本次功能。私有仓库需要在服务器配置 Git 访问权限；可以把服务器生成的公钥设为仓库的只读 Deploy key，再使用 SSH clone 地址。不需要把私钥写入项目或镜像。

`.env` 填写现有的 OSS、Ark、DeepSeek 凭证及固定 `ENCRYPTION_MASTER_KEY`。已有数据库必须沿用原主密钥。服务器建议明确设置：

```dotenv
KB_PORT=8080
COMPOSE_PROJECT_NAME=course-knowledge
KB_HOST_DATA_DIR=/srv/course-knowledge-data
KB_STORAGE_BACKEND=oss
OSS_DEV_BUCKET=futuredev
OSS_PROD_BUCKET=futureprod
AUTH_DEV_UPSTREAM_BASE_URL=https://futuredev.artz.zone/api
AUTH_PROD_UPSTREAM_BASE_URL=https://future.artz.zone/api
```

8080 如果被其他服务占用，选择空闲端口，并同步修改 Nginx 片段的两个 `proxy_pass`。不要沿用先前端口快照认定它一直空闲。

### 从本机当前配置生成服务器初始化脚本

本机 `.env` 已填好凭证时，可在本机后端目录执行（Windows 使用 `py -3`，Linux 使用 `python3`）：

```powershell
py -3 deploy/export_server_env.py
scp .env.server-init.sh root@39.106.204.62:/workspace/course-knowledge/.env.server-init.sh
```

生成的 `.env.server-init.sh` 是包含当前 Ark、DeepSeek、OSS 凭证的私密文件，已由 `.env.*` 规则排除于 Git 和 Docker 构建上下文；仅导出器代码可以提交。通过 SSH 单独传输这一个文件，不把它发布到仓库。在服务器执行：

```bash
cd /workspace/course-knowledge
sh .env.server-init.sh
sh deploy.sh
```

初始化脚本只写同目录的 `.env`，权限为 600；默认端口 8080，持久目录 `/srv/course-knowledge-data`，保持 dev/prod 认证接口、SQLite 和 OSS 分离。它不复制 Windows 工具路径、本机数据库路径或本机加密主密钥。新安装自动生成 32 字节随机主密钥；已有配置优先保留服务器填写的非空值，尤其是主密钥与数据目录，只补齐缺项。需要修改既有非空配置时直接编辑服务器 `.env`。发生配置变化时先生成私密 `.env.backup-*` 备份，重复运行不重新生成密钥。发现已有数据库但缺少主密钥时停止，不会用新密钥覆盖。脚本不改 Nginx、不启动容器、不迁移资料。

```bash
ss -lntp 'sport = :8080'
sh deploy.sh
```

`sh deploy.sh` 是后端的一键更新命令：自动拉取 Git、构建新的后端镜像、用新镜像更新容器，并启动 Rust 与 Qdrant。Nginx 配置由站点维护者单独处理，不包含在此命令内；前端也继续独立打包发布。

脚本默认拉取 `origin/master`，只允许当前分支为 `master` 且工作区干净。可以用 `--branch 分支名 --remote 远端名` 指定；先手动检出对应分支。忽略于 Git 的 `.env` 和 `data/` 不阻止部署。

脚本依次执行：加部署锁 → 检查 Git / Docker → fetch 与 fast-forward → 验证运行配置、端口和持久目录 → 构建镜像 → 启动两项服务并等待健康检查 → 分别检查 dev、prod 就绪状态。

配置按字面值由 Compose 解析，不执行 `.env` 的 shell 内容。正常构建使用提交 SHA 作为 Rust 镜像标签。构建期间旧容器继续运行；替换 API 时存在短暂停机。构建失败不会进入容器替换，启动失败返回非零并保留现场，便于查日志。脚本不做自动数据回滚；数据库迁移后仅替换旧镜像未必兼容。

首次启动会创建专用数据目录；以 root 运行时仅为新建的 Rust 目录设置 uid/gid 10001。已有目录或 SQLite 文件权限不符时停止，不递归修改所有权。非 root 部署可先由管理员准备目录：

```bash
sudo install -d -o 10001 -g 10001 -m 0750 /srv/course-knowledge-data
sudo install -d -o 10001 -g 10001 -m 0750 /srv/course-knowledge-data/dev /srv/course-knowledge-data/prod /srv/course-knowledge-data/cache
sudo install -d -m 0750 /srv/course-knowledge-data/qdrant
```

默认 Rust / Qdrant 各限 0.5 CPU、768 MiB，日志各保留最多 3 × 10 MiB。容器运行限制不限制 Docker 构建器；Rust 编译已经设为单任务，但第一次 release 构建仍可能占用较多内存。2 核 4 GiB 机器还运行原业务，可在另一台 Linux 构建机先构建镜像，再执行以下方式：

```bash
# Linux 构建机，同一提交的后端源码目录
kb_release_sha=$(git rev-parse HEAD)
export KB_SERVICE_IMAGE="3dcourse-knowledge-service:$kb_release_sha"
docker compose --env-file .env build qdrant knowledge-service
docker save -o course-knowledge-images.tar "$KB_SERVICE_IMAGE" 3dcourse-qdrant:1.14.1

# 传输 tar 到服务器，先将服务器源码更新到同一提交并保持在 master 分支
# 服务器 .env 中设置 KB_SERVICE_IMAGE=3dcourse-knowledge-service:<上面完整 SHA>
docker load -i course-knowledge-images.tar
sh deploy.sh --no-pull --no-build
```

## 二、单独配置 Nginx

以下步骤独立于部署脚本。根据此前只读核查，生产配置是 `/etc/nginx/conf.d/future.conf`，开发配置是 `/etc/nginx/conf.d/future-test.conf`。编辑前确认这两个文件仍为实际站点配置。片段必须位于两个站点的 **HTTPS `server {}` 内部**，不能作为顶层 conf.d 文件直接加载。

在后端仓库目录执行：

```bash
sudo install -d -m 0755 /etc/nginx/snippets
sudo install -m 0644 deploy/nginx-kb.conf /etc/nginx/snippets/course-knowledge.conf

kb_nginx_backup_stamp=$(date +%Y%m%d-%H%M%S)
sudo cp -a /etc/nginx/conf.d/future.conf "/etc/nginx/conf.d/future.conf.$kb_nginx_backup_stamp.bak"
sudo cp -a /etc/nginx/conf.d/future-test.conf "/etc/nginx/conf.d/future-test.conf.$kb_nginx_backup_stamp.bak"

sudo nano /etc/nginx/conf.d/future.conf
sudo nano /etc/nginx/conf.d/future-test.conf
```

分别在 `server_name future.artz.zone;` 和 `server_name futuredev.artz.zone;` 对应的 HTTPS server 内加入一行，仅加一次；如已有 `/kb-api/` location，更新旧片段，避免重复：

```nginx
include /etc/nginx/snippets/course-knowledge.conf;
```

片段内容见 [nginx-kb.conf](nginx-kb.conf)。它转发 `/kb-api/`，保留 `Host $host`，关闭代理缓冲并允许最长 900 秒读取，支持会话 SSE 和媒体 Range。这里的 `proxy_pass http://127.0.0.1:8080;` 没有末尾 `/`，保留完整 `/kb-api/...` 请求路径。原 `/api/admin`、`/api`、`/ws` 和静态文件路由继续由各自原配置负责。

检查成功后加载并验证两个站点：

```bash
sudo nginx -t && sudo systemctl reload nginx
curl --fail --silent --show-error https://futuredev.artz.zone/kb-api/v1/readyz
curl --fail --silent --show-error https://future.artz.zone/kb-api/v1/readyz
```

后端脚本不会编辑或重载 Nginx。参考 [Nginx 代理文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html) 关于 Host、`proxy_pass` 和缓冲的规则。

## 三、后续更新与排查

```bash
cd /workspace/course-knowledge
sh deploy.sh

# 使用外置配置文件
sh deploy.sh --env-file /etc/course-knowledge/service.env

# 已手动更新当前分支，仅构建/启动，不拉 Git
sh deploy.sh --no-pull

# 仅查看这一套知识库服务
docker compose -p course-knowledge ps
docker compose -p course-knowledge logs --tail 100 knowledge-service qdrant
docker compose -p course-knowledge logs -f --tail 100 knowledge-service

# 单独停止知识库；再次 sh deploy.sh 可启动
docker compose -p course-knowledge stop knowledge-service qdrant
```

部署流程依据 [Git 的 fast-forward 规则](https://git-scm.com/docs/git-merge) 和 [Compose 的 up / wait 行为](https://docs.docker.com/reference/cli/docker/compose/up/)。`--no-pull` 仍要求工作区干净并处于指定分支，不会自动切换、提交或丢弃代码。

持久目录包含 dev / prod SQLite、Qdrant、可回收缓存和 `logs/ai/{dev,prod}`。每次问答会写一个以开始时间、会话名称、用户 ID 和会话 ID 命名的 JSON trace，内容包括检索片段、模型输入输出、校验结果和各阶段耗时；媒体 URL 会脱敏。trace 可能包含课程正文和学生问题，只允许服务器管理员读取，不要通过 Nginx 暴露。原件继续在 OSS。换代码或镜像时保留数据目录与主密钥。首次使用空持久目录会创建空知识库，同一个 OSS 桶不会自动重建 SQLite 中的课程、发布和会话记录。要带入既有本机资料，需要另行一致性迁移 SQLite 和 Qdrant，并确认资料属于哪一套环境。

当前仅准备脚本和文档，没有连接服务器执行部署。本机可验证脚本控制流程和 Rust；Docker 构建、Linux 权限和线上 Nginx 需要在实际部署环境验证。
